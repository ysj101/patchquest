# 課題を、持ち帰ることと仕組みの理解から設計する

課題は、解けることが目的ではない。解いた人が、自分の職場の機械やコードで同じ問題に気づき、直せるようになることが目的である。

出荷前検証（`verify:packs`）と学習者としての通し（[playtest-mission](../playtest-mission/SKILL.md)）は、「解ける」ことを確かめる。**解いて何が残るか**は確かめない。この手順は、その部分を作る前に決める。

過去に、解けるのに学びが残らなかった例（課題「更新を、確かめてから取り込む」の初版）：

- 直す操作が、教材だけにある設定ファイル（`/etc/update.conf`）の `verify=off` を `verify=on` に書き換えることだった。実在の機械にこのファイルはないので、学習者は自分の機械で何を見ればよいかを持ち帰れなかった。
- ハッシュを照らし合わせる処理は、プログラムの中で動くだけだった。学習者はハッシュの値を一度も見ず、中身を変えると値が変わることも確かめなかった。解き終えても「ハッシュを比べる」が何をしているのか分からなかった。

どちらも、仕組みは本物（本物の `sha256sum`）で、テストも通しの確認も通っていた。

## いつ行うか

- 課題パックを新しく作る。
- 既存の課題の題材・直し方・調べ方の手順を変える。
- 課題のために、教材アプリへファイル・コマンド・設定を足す。

案内文の言い回しだけを直すときは行わなくてよい。

## 1. 持ち帰ることを先に書く

題材や画面を考える前に、次の 3 つを書く。書けないうちは実装を始めない。

1. **持ち帰ること**：解いた人が、翌日、自分の機械やコードで何を開き、何を確かめ、どう直すか。実在のファイル・コマンド・コードの書き方の名前で書く。
   - 良い例：「`sudo -l` で、自分に許されたコマンドを確かめる。`/etc/sudoers` に、書き換えられるプログラムへの許可がないかを見る」
   - 悪い例：「更新は確かめてから取り込むべきだと分かる」（心がけだけで、何を開くかが分からない）
2. **理解してもらう仕組み**：なぜ攻撃が成り立ち、なぜその対策で止まるのかを、因果で 2〜3 文に書く。
   - 例：「ファイルの中身からハッシュを計算すると、1 文字変えただけで値がまったく変わる。配布元が出した値を別の場所に持っておき、受け取ったものの値と比べれば、途中で書き換えられたことに気づける」
3. **実物との対応**：課題に出てくるファイル・コマンド・設定のそれぞれが、実物の何に当たるか。当たるものがないものは、なぜ必要かを書く。

この 3 つは PR の本文に載せる。実物の名前や挙動は、記憶で書かずに確かめる。確かめていないものは、そう書く。

## 2. 題材を実物に寄せる

- **独自の仕組みを作らず、広く知られている仕組みを使う。** 課題のために、独自のプログラム・独自の設定・独自の確認の手順を考え出さない。まず、同じ問題を扱う、広く使われている仕組み（OS やパッケージ管理の機能、標準のコマンド、よく使われるライブラリや書き方）を探し、それを題材にする。初版の例では、独自の取り込みプログラム（`apply-update`）と独自の設定を作った。配布元が出す `SHA256SUMS` を `sha256sum -c` で確かめる手順や、パッケージ管理の署名の確認を、そのまま題材にできた。
- **実在の名前・書式・コマンドを使う。** 学習者が検索して、同じものが見つかる題材にする（`/etc/sudoers`・`visudo`・`sudo -l`、SQL のプレースホルダ、`sha256sum -c` と `SHA256SUMS`、apt の署名の確認など）。
- **直す操作を、教材だけにあるスイッチの切り替えにしない。** 独自の設定を `off` から `on` に変える課題で身に付くのは、その課題の解き方だけである。直す操作は、実物でも同じ形で行う操作にする。
- **広く知られている仕組みが見つからない・使えないときは、独自に作る前に人に相談する。** 何を探し、なぜ使えなかったかを添える。
- **実物をそのまま動かせないときは、作りものを最小にする。** 仕組みの中心（比べる・確かめる・拒む処理）は実物を使い、作るのは周りの入れ物だけにする。
- **作りものは、作りものだと学習者に伝える。** 振り返りに、「この課題の ○○ は教材用。実際の機械では △△ がこれに当たる」と、実物の名前で書く。学習者が教材の名前を実物だと思って持ち帰らないようにする。

## 3. 仕組みを、学習者の手で見えるようにする

仕組みがプログラムの中だけで動く課題は、解けても理解が残らない。「理解してもらう仕組み」の文に出てくる出来事を、1 つずつ、学習者が自分の操作で起こして、結果を目で見る手順にする。

- **値や状態を、学習者が自分で出す。** 比べる・確かめる対象（ハッシュの値、権限、条件式、出力された HTML）を、学習者がコマンドや操作で表示する。プログラムが「合いません」と言うだけにしない。
- **変える前と変えた後を並べて見る。** 「変える前の値を見る → 1 か所変える → もう一度見る → 違いに気づく」の順にする。仕組みの因果は、この差で伝わる。
- **対策が止める瞬間を見る。** 直した後に、同じ攻撃をもう一度行い、どこで、何と比べて止まったかが画面に出るようにする。
- **なぜ別の直し方では足りないかを、試せるようにする。** よくある誤った直し方（置き場を守るだけ、機能ごと止める）を試すと、どのテストがなぜ落ちるかが文から分かるようにする。
- **調べ方（`approach`）とヒントは、設定の場所ではなく、仕組みを見る操作へ導く。** 「設定のファイルを読みましょう」より先に、「中身を変えると値がどう変わるかを見ましょう」を置く。
- **理解確認（`transferCheck`）は、仕組みを別の場面に当てはめられるかを聞く。** 課題の手順を覚えているかを聞かない。

手で見せる出来事が多すぎて 1 つの課題に収まらないときは、仕組みを分けて課題を 2 つにする。見せるのを省かない。

## 4. 作る前の点検

次の問いに、すべて「はい」と答えられてから実装する。

- 持ち帰ることを、実在のファイル・コマンド・コードの名前で書いたか。
- 題材は、広く知られている仕組みか。課題のために独自の仕組みを作っていないか。
- 直す操作は、実物でも同じ形で行う操作か。教材だけのスイッチを切り替えていないか。
- 仕組みの文に出てくる出来事を、学習者はそれぞれ自分の操作で起こし、結果を見るか。
- 学習者は、課題のコードを読まずに、画面に出た結果だけから仕組みを説明できるようになるか。
- 作りものの部分と、実物での対応を、学習者に見える文に書いたか。

迷う点（実物をどこまで再現するか、仕組みをどこまで見せるか）は、推測で決めずに人に確認する。

## 5. 作った後の確かめ

[playtest-mission](../playtest-mission/SKILL.md) の通しで「解決」まで進めたあと、コードを見ずに、画面に出た文と結果だけを頼りに次を書く。

- この課題の仕組みを、因果で 2〜3 文に。
- 自分の機械で、明日、何を開いて何を確かめるか。

手順 1 で書いた文と比べる。書けない・食い違うときは、課題が伝えていない。案内文を足して済ませず、手順 3 に戻って、見える操作を足す。

## 報告

PR の本文に、次を書く。

- 持ち帰ること・理解してもらう仕組み・実物との対応（手順 1）。
- 学習者が手で見る出来事の一覧と、それを見る操作（手順 3）。
- 作りものの部分と、それを学習者に伝えている場所。
- 作った後の確かめで書いた文と、手順 1 との違い。
