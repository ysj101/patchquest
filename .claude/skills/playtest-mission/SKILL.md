# 課題を学習者として解いて確かめる

自動テスト（`pnpm run check`・`test:e2e`・`verify:packs`）は、「正しい操作を送れば合格する」ことを確かめる。学習者が**その操作にたどり着けるか**は確かめない。この手順は、その部分を確かめる。

過去に自動テストが全部通ったまま出荷して、学習者が解けなかった例：

- 画面の案内が「help と入力すると、使えるコマンドを表示します」と勧めるのに、`help` が調べるのに使うコマンドを出さなかった。
- 直すのに使うコマンド（`edit`）が実在しないもので、引用符の付け方でつまずいた。
- 調査タブの操作を送っても、結果が教材アプリの画面に出なかった。
- 端末の課題なのに、観測ログが HTTP のリクエストと状態コードで表示された。
- 入力欄を正確に押さないと、キーを打っても入力されなかった。

どれも、テストが使う近道（`fill` で値を入れる、要求を直接送る、正解の操作を知っている）では見つからない。

## いつ行うか

- 課題パックを新しく作った。
- 課題パックの題材や解き方を変えた（[design-mission](../design-mission/SKILL.md) を使う場合と同じ範囲）。実装のあとに、design-mission の「作った後の確かめ」と組で行う。

教材アプリの画面・コマンドの受け付け方・学習者に見える文（導入・「今やること」・調べ方・ヒント・解法・画面の中の案内）だけを変えたときは、行わない。この種の変更は、E2E で守っている範囲を、マージ後の CI で確かめる。

## 守ること

1. **製品ビルドで試す。** `node scripts/build.mjs`（`--test` を付けない）で作った `dist/` を配信する。テスト用のカタログやテスト用のパックで代用しない。
2. **まっさらなブラウザで始める。** 進捗が残っていない状態から、課題一覧のカードを押して始める。
3. **学習者と同じ操作だけを使う。** クリックと、1 文字ずつのキー入力（`page.keyboard.type`）で進める。`fill`・`evaluate` での値の設定・要求の直接送信・ページの内部の関数は使わない。入力欄を狙って押すのではなく、学習者が押しそうな場所（端末なら出力のあたり）を押してから打つ。
4. **正解を知らないつもりで進める。** 次の一歩は、その時点で画面に出ている文から決める。コードやテストを見て知っている操作を、画面に手がかりがないまま打たない。手がかりがなければ、それが見つけた問題である。
5. **画面に出ている案内は、書いてあるとおりに全部試す。** 「〜と入力すると…」「〜を押すと…」と書いてあれば、そのとおりに行い、書いてあるとおりの結果になるかを見る。案内に出てくるコマンド名・ボタン名・ファイル名は、1 つずつ実際に使う。
6. **要所で画面を見る。** スクリーンショットを撮って自分の目で確かめる。文字の折り返し・はみ出し・重なり、結果が見える場所に出ているか、題材に合った言葉で表示されているかを見る。`expect` が通っただけで済ませない。

## 手順

### 1. 起動

```bash
node scripts/build.mjs
PORT=4190
python3 -m http.server "$PORT" --bind 127.0.0.1 --directory dist >/dev/null 2>&1 &
```

使っていないポートを選び、終わったら自分が起動したサーバだけを止める。

### 2. 通しで解く（ヒントを開かない）

Playwright（`@playwright/test` の `chromium`、`channel: 'chrome'`）でスクリプトを書いて進める。スクリプトとスクリーンショットは作業用の場所に置き、リポジトリには入れない。

教材アプリは隔離 iframe の中にある。キー入力は、iframe の中の要素を押してからページへ送る。

```js
const frame = page.frameLocator('.preview-slot iframe');
// 入力欄ではなく、学習者が押しそうな場所を押してから打つ
await frame.getByRole('log', { name: '端末の出力' }).click({ position: { x: 40, y: 20 } });
await page.keyboard.type('sudo -l', { delay: 10 });
await page.keyboard.press('Enter');
```

次の順に進め、各段で「画面のどの文を頼りに、何をして、何が起きたか」を記録する。

1. 課題一覧 → 開始前チェック → 導入。待ち時間を測る。
2. **調べる**：最初の画面の案内と「今やること」（いまのステージの印にマウスを乗せると出る）・調査タブの調べ方に従う。
3. **再現する**：再現の達成印が付くまで。
4. **直す**：正しい直し方で、防御の達成印が付くまで。
5. **検証する**：結果の文が、何が起きたかを伝えているか。
6. **直した後の確認**：演習中の画面でも、攻撃が防がれ、普段の使い方が通ること。
7. **理解確認に答える**：状態が「解決」になるまで。
8. **残ったことを書く**：コードを見ずに、画面に出た文と結果だけを頼りに、課題の仕組み（なぜ攻撃が成り立ち、なぜ対策で止まるか）と、自分の機械で明日何を開いて確かめるかを書く。書けないときは、解けても学びが残らない課題である。[design-mission](../design-mission/SKILL.md) の手順 3 に戻る。

### 3. つまずきそうな道も試す

- **誤った直し方**（絞りすぎ・足りない直し方）を 1 つ行い、検証で不合格になること、何が足りないかが文から分かることを確かめる。
- **「初期状態へ戻す」** で、やり直せること。
- **学習者が打ちそうな別の書き方**を試す（相対パス、別の利用者のまま実行、よくある打ち間違い、使えないコマンド）。断るときは、理由と次にすることが分かる文になっているか。
- **ヒント 1 → 2 → 3 と解法**を順に開き、書いてある操作をそのとおりに行って解けることを確かめる。ヒントに出てくる行番号・パス・ボタン名が、画面と合っているか。
- **キーボードだけ**で主要な操作ができること（spec A22）。

### 4. 記録するもの

- コンソールのエラーと、ページのエラー（`page.on('console')`・`page.on('pageerror')`）。
- 外部への通信（`page.on('request')` で、配信元以外への要求がないこと）。
- 開始からクリアまでの時間と、待たされた場所。

## 見つけたら

- 学習者が次の一歩を決められない・案内どおりにならない・結果が見えない、は不具合として直す。直したら、通しで解くところからやり直す。
- 見つけた道が自動テストで守られていなければ、E2E を足す（`missions/<課題>/__tests__/` か `tests/e2e`）。
- 直さずに残すものは、理由を添えて報告に書く。

## 報告

完了の報告と PR には、次を書く。

- 試した操作と結果の表（調べる・再現・直す・検証・解決まで。誤った直し方とヒントの確認も）。
- 開始からクリアまでの時間。
- 見つけて直したこと、直さずに残したこと。
- **確かめていないこと**（実際の日本語入力、Chrome 以外のブラウザ、公開サイトなど）。確かめていないものを「確かめた」と書かない。
- 再現できなかった報告を直したときは、再現できなかったことと、直した内容が原因だったかは分からないことを書く。
