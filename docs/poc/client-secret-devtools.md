# PoC: 画面側のコードに置いた秘密を DevTools で見つける課題

Issue #236。「画面側（フロント）のコードや保存領域に置いた秘密は、誰でも読める」ことを、学習者が Chrome の DevTools で確かめる課題を、いまの実行環境（隔離 iframe ＋ Worker）の上に作れるかを確かめた。

## 結論

**いまの実行環境の上では作らない。見送りを勧める。** 理由は次の 3 つ。

1. **画面側とサーバ側の境目を、DevTools の上では本物として見せられない。** サーバ役の Worker は、学習者が開く同じ DevTools に並ぶ。コードは元のソースのまま読め、メモリにしかない値も読めた（下の「サーバ役」）。「秘密をサーバ側へ移せば読めない」ことを、この環境で学習者が自分の目で確かめることはできない。spec §14 の「ブラウザ内にすべて存在する教材データを、利用者自身から秘匿できるとは扱わない」とも両立しない。
2. **Issue が挙げた 3 つのパネル（Sources・Application・Network）のどれにも、題材に当たるものが出ない。** Sources に出る枠のスクリプトは、ビルド時に決まる 1 本で、すべての課題の実装が入っている。直す前と後で変わらない。Application には、枠の保存領域がない（不透明なオリジンなので `localStorage` を使えない）。Network には、教材アプリのやり取りが 1 件も出ない。
3. **学習者が DevTools で行う操作を、E2E でも playtest でも確かめられない。** Playwright は DevTools の画面を操作できない。CDP で同じ情報が取れることは確かめられるが、「画面の案内だけで、パネルを開いて鍵にたどり着けるか」は確かめられない。課題の中心になる操作が、確かめないまま出荷されることになる。

課題パックは作っていない。この記録と、測定を再現する E2E だけを残す。

## 結果

### 画面側（隔離 iframe）

| 確認項目（当たるパネル） | 結果 |
| - | - |
| 枠のオリジン | `null`（不透明）。DevTools からは、ページとは別のターゲット（`iframe`）として見える |
| 枠の `localStorage`・`sessionStorage`・`document.cookie`・`indexedDB.open`（Application） | どれも SecurityError（`The document is sandboxed and lacks the 'allow-same-origin' flag.`）。枠には、鍵を置ける保存領域がない |
| 枠の中での式の評価（Console） | できる（`1+1` が `2`）。枠の CSP は、DevTools からの評価を止めない |
| 枠の DOM（Elements） | 読める。画面に描いたものは、そのまま見える |
| 枠のスクリプト（Sources） | `assets/preview.html` に埋め込んだ 1 本だけ（製品ビルドで約 208 KB、圧縮済み、ソースマップなし）。配信している静的なファイルの中身と同じ |
| 枠のスクリプトの中身 | 画面側の処理だけでなく、サーバ役で動く処理（メモ帳の検索クエリ `owner_id = ?` など）、別の教材アプリ（Linux 端末）の語（`sudoers`）、課題の文（対策の名前など。日本語は `\uXXXX` の形）も入っている。カタログ全体を 1 本にまとめているため |
| 教材アプリを操作したときの通信（Network） | 0 件。画面からメモを 1 件取り出して本文が出るまでの間、ページと枠のどちらにも `Network.requestWillBeSent` が出ない。やり取りは `postMessage` で運んでいる |

枠のスクリプトは、ビルド時に作り、そのハッシュを枠の CSP に書いている（`scripts/build.mjs` の `buildSandboxDocument`）。演習ごと・選んだ対策ごとに中身を変えることはできない。

### サーバ役（Worker）

| 確認項目 | 結果 |
| - | - |
| DevTools からの見え方 | ページの下のターゲット（`worker`、名前は `patchquest-runtime`）として見える。測定のときは 2 つあった（どちらが何に使われているかは調べていない。画面の操作で止まったのは 1 つだけ） |
| Worker のスクリプト（Sources） | `assets/runtime-worker.js`。ソースマップ（`runtime-worker.js.map`）が付いていて、元のソース 70 ファイルの中身を含む。`apps/memo/server.ts`（サーバ役の処理）も、`missions/*/learning.ts`（ヒント・解法・振り返りの文）も、元の TypeScript のまま読める |
| Worker のメモリにしかない値 | **読めた。** bob の画面には bob のメモしか届いていない状態で、Worker を次の文で止め（`Debugger.pause`）、止まった場所から見える変数をたどって、SQLite から alice・bob・carol の非公開メモの本文を取り出せた。DevTools では、Sources でブレークポイントを置いて Console で式を打つ操作に当たる |

### 学習UI（参考）

観測ログは、教材アプリの画面が送ったやり取りも含めて、リクエストと応答の本文をそのまま出す（`platform/ui/investigation.ts`）。応答で画面側へ鍵を渡す作りにすると、DevTools を開かなくても、観測ログに鍵が出る。

## Issue の「決めること・確かめること」への答え

| 項目 | 分かったこと |
| - | - |
| 「サーバ側」の表し方 | Worker は同じ DevTools から、コードもメモリも読める。境目を本物として見せられない。Service Worker の方式（#232）を使っても、サーバ役がブラウザの中にあることは変わらない（下の「何が要るか」） |
| DevTools を使う案内 | 案内の文は書けるが、その案内で進めるかを自動では確かめられない。CDP で確かめられるのは、「パネルに出るはずの情報がある」ことまで。DevTools の表示の言語（英語・日本語）による名前の違いも、確かめる手段がない |
| 合否の判定 | プラットフォームが観測できるのは、教材アプリとのやり取り（リクエスト・応答・観測イベント）だけ。DevTools で鍵を見たことは観測できない。見つけた鍵を使ったリクエストを送らせ、その鍵が初期データの値と合うことで再現とみなす形（`ProbeDef.detect`）なら作れる見込み（未実装・未測定） |
| 鍵の作り直し | 実物では、鍵を発行したサービスの管理画面で、無効にして発行し直す。手元のコマンドや書式のように、広く共通する形がない。教材に入れるには、架空の管理画面を作ることになり、教材だけの仕組みになる。この課題では操作にせず、振り返りの文で伝えるにとどめるのがよい（#230 と合わせて決める） |
| 新しさ | 技術の追加は要らないと見ていたが、実際には実行環境の追加（下）が要る |

## design-mission の点検に照らすと

いまの実行環境の上で考えられる最も近い形は、「サーバ役が応答で鍵を画面側へ渡し、画面側がそれを見えない形で持つ。学習者は Elements か Console で見つける。直すときは、鍵を使う処理をサーバ役へ移した実装を選ぶ」である。これを、作る前の点検（`.claude/skills/design-mission/SKILL.md` の 4）に当てると、次が「はい」にならない。

- **題材は、広く知られている仕組みか。** 鍵を使う先の外部サービス・その鍵・鍵を配る口を、すべて教材のために作ることになる。実物で鍵を見つけるときに使う Sources の検索・Network のヘッダ・Application の `localStorage` は、どれも使えない。
- **仕組みの文に出てくる出来事を、学習者は自分の操作で起こし、結果を見るか。** 「サーバ側へ移すと、ブラウザには届かない」を、学習者は DevTools で確かめられない。同じ DevTools に、サーバ役のコードとメモリが出ている。直す前と後で、Sources に出るスクリプトも変わらない。
- **作りものの部分と、実物での対応を伝えたか。** 伝えることはできるが、「この教材ではサーバ側もブラウザの中にある」という断りが、課題の持ち帰ること（ブラウザに届いたものは秘密にできない。秘密はサーバ側に置く）そのものと食い違う。

## 何が要るか

進めるなら、次がそろってからにする。

- **応答ごとに中身が決まる文書を、本物の HTTP 応答として返す実行環境（#232）。** Service Worker が文書を返す方式なら、Network に本物のリクエストと応答が出る（`docs/poc/service-worker-http.md` で測定済み）。文書に埋め込むスクリプトも応答ごとに作れるので、鍵を埋めた版と埋めていない版を出し分けられ、直す前と後の差が Sources に出る見込み（未測定）。
- **サーバ役がブラウザの中にあることの扱いを、先に決める。** #232 の方式でも、Service Worker と Worker は同じ DevTools に出る。課題の主張を「サーバ側に置けば読めない」ではなく「届いた文書と通信に、鍵が入っているかどうか」に絞り、学習者に見せる範囲を教材アプリの枠（文書・通信）に限る必要がある。それで持ち帰ることが伝わるかは、人が決める。
- **`localStorage` は題材から外す。** いまの枠でも、#232 の方式（応答の CSP `sandbox`）でも、教材アプリの文書は不透明なオリジンで、保存領域を使えない。隔離をやめれば使えるが、Host の保存領域（進捗）に届くので採れない。
- **DevTools の操作を確かめる手順。** 自動では確かめられないので、人が DevTools を開いて案内どおりに進める確認を、出荷の条件に足すかを決める。

別の案として、本物の Linux の端末（`apps/shell/linux`）で、公開するディレクトリの下のファイルに鍵が書いてあることを `grep` で見つける課題にする道もある。実在のコマンドだけで作れるが、DevTools を使う課題ではなくなり、#230 と題材が近い。試していない。

## 確かめていないこと

- DevTools の画面を人が開いて、各パネルに上の情報が実際にどう並ぶか（CDP で同じ情報が取れることだけを確かめた）。
- #232 の方式で、文書に埋め込んだスクリプトが Sources にどう出るか、直す前と後で差が見えるか。
- 見つけた鍵をリクエストに入れて送らせる形の、再現の判定。
- Chrome 以外のブラウザ。
