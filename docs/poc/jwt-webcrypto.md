# PoC: WebCrypto で、ログイントークン（JWT）の署名と検証を行う

Issue #237。署名を確かめずにログイントークンを信じることを題材にした課題の前提として、教材ロジックを動かす Worker の中で、本物の署名と検証（HMAC-SHA256）が使えるかを確かめた。

## 結論

**採用する。** トークンは本物の JWT（RFC 7519）の形にし、署名は HS256（HMAC-SHA256）を WebCrypto（`crypto.subtle`）で計算する。追加の配布物は要らない。通信・保存の API を塞いだあとの Worker でも動き、同じ鍵と中身からはいつも同じトークンになる。課題パックは `missions/jwt-signature/` として実装した。

## 結果

| 確認項目 | 結果 |
| - | - |
| 塞いだあとの Worker での WebCrypto | `lockdown()` のあと（`fetch` を読むと例外になる状態）で、`crypto.subtle.importKey`・`sign`・`verify`（HMAC、SHA-256）が動いた。`lockdown()` が塞ぐのは通信・保存・別の実行環境を作る API で、`crypto` は含まない |
| 安全なコンテキスト | `http://127.0.0.1` で配信した Worker で `isSecureContext` は `true`。`crypto.subtle` は安全なコンテキスト（HTTPS か localhost）でだけ使える。配布の前提（静的 HTTPS 配信か localhost、spec §12）と同じ |
| 本物の JWT と同じ結果になるか | JWT の例として広く引用されているトークン（鍵 `your-256-bit-secret`、中身は `John Doe` のもの）と同じ鍵・同じ中身から、署名まで同じトークンができた（`tests/unit/memo-token.test.ts`） |
| 決定的か | 同じ鍵と同じ「ヘッダー.中身」から、署名は毎回同じ値になった。Chrome の Worker と Node.js でも同じトークンになった。HMAC は乱数を使わない |
| 書き換えの検出 | 中身を `{"sub":"bob"}` から `{"sub":"alice"}` に替え、署名を元のまま付けたものは、`verify` が `false` を返した |
| 時間（Chrome の Worker） | 鍵の取り込み 0.2〜0.3ms、最初の署名 0.1ms 以下。鍵の取り込み・署名・検証を 1000 回くり返して 10〜15ms（3 回計測） |
| 時間（Node.js） | 同じ 1000 回のくり返しで 62〜129ms（3 回計測） |
| 検証の時間の上限 | テスト 1 件 5 秒・スイート 60 秒（spec §14）に対して、このパックの出荷前検証（3 つの seed、対策 3 つと検証専用の候補 3 つ）は、ブラウザで全体が 10.9 秒だった。1 件のテストが行う署名と検証は数回なので、上限には遠い |
| 外部通信 | 演習を最初から「解決」まで行うあいだ、配信元以外への要求は 0 件だった |

## 実装への反映

- **鍵**：初期データ生成器（`apps/memo/fixtures.ts`）が、seed から 32 バイトの鍵を作って `token_keys` の表に入れる。教材ロジックだけが読み、応答には出さない。乱数の列はメモなどの初期データと分けたので、鍵を足しても既存の初期データ（利用者やメモの ID・内容）は変わらない。
- **初期データ生成器は同期のまま**：署名は非同期（`crypto.subtle` は Promise を返す）なので、初期データ生成器では署名しない。正しいトークンは、テストの手順で発行して取り出す（`capture`）。初期データに入れるのは、鍵を使わずに組み立てられるトークン（でたらめな署名を付けたもの・「署名なし」を名乗るもの）だけにした。
- **教材ロジックの応答**：`AppModule.handle` は Promise を返せるので（Linux 端末のために足してあった）、プラットフォームと実行環境は変えていない。
- **署名の方式**：検証は HS256 に固定し、ヘッダーの `alg` が別の値のトークンは計算せずに断る（「署名なし」を表す `none` を受け付けない）。
- **合否の根拠**：教材ロジックは、交換点（`memo.token.verify`）の判断とは別に、署名が鍵で計算した値と合うかを測り、観測イベント `token.checked` に並べて記録する。攻撃阻止のテストと再現の判定は、「署名の合わないトークンを受け付けた」という記録と、返ったメモの持ち主で決める。

## 安全（現実に転用できる手口にならない範囲か）

- 学習者が行うのは、自分に発行されたトークンの中身を読み、名前を書き換えて、同じ教材アプリへ送ることだけである。JWT の中身が署名なしでも読めること・受け取る側が署名を確かめなければならないことは、RFC 7519 と各ライブラリの説明に書かれている、広く知られた内容である。
- 鍵を当てる・推測する道具、署名を偽造する道具は置いていない。教材アプリの「トークンを調べる」は、base64url を元の文字に戻す・文字を base64url に直すだけで、鍵を使う処理は教材ロジック（Worker）の中にしかない。
- トークンを受け付けるのは、ブラウザの中の教材ロジックだけである。外部へは送らない（外部通信 0 件を計測した）。

## 注意点

- 鍵は、初期データを再現できるよう、seed から決まる疑似乱数（`apps/shared/random.ts`）で作っている。実際のサービスの鍵は、暗号用の乱数で作り、コードやデータベースの外（環境変数など）に置く。
- 実際の JWT には期限（`exp`）などを入れる。この教材のトークンの中身は利用者の名前（`sub`）だけで、時刻を入れていない（同じ seed から同じトークンにするため）。
- リクエスト相当の呼び出し（`AppRequest`）にはヘッダーがないので、トークンは要求の本文に入れて送る。実際のサービスで一般的な `Authorization: Bearer` ヘッダーとは違う。振り返りの「覚えておくこと」に、その違いを書いた。
- 計測値は上記の端末での参考値で、性能の保証ではない。
