# 効果の検証：指標の定義と手元での計測手順

ゲーミフィケーション改善（[patchquest-gamification-improvements.md](patchquest-gamification-improvements.md) §6）の効果を、機能追加の前後で比べるための指標と手順。利用履歴の外部送信はしない（[spec.md](spec.md) §16）。参加者が自分で書き出した進捗 JSON と、同意のある観察セッションの記録だけを使う。

## 1. 守ること

- **ランキング・連続ログイン数・滞在時間を成功指標にしない**。spec §9 の方針どおり、これらは表示にも評価にも使わない。
- 指標は進捗 JSON から**機械的に再計算できる**ものと、観察で**本人に聞く**ものに分ける。混ぜない。
- 進捗 JSON は本人が書き出して渡したものだけを使う。ブラウザの保存領域を直接読まない。
- 集計はローカルで行い、個人が特定できる形で共有しない（ファイル名は参加者番号にする）。
- 達成印「再現・防御・理解」の判定は変えない。指標のためにしきい値を調整しない。

## 2. 進捗 JSON から出す指標

参加者 1 人につき進捗 JSON 1 ファイル（画面の「進捗を書き出す」で得られる `patchquest-progress-<日付>.json`）。形式は `platform/progress/schema.ts` の `ProgressFile`。集計スクリプト `scripts/evaluation-metrics.mjs` は、この表の定義をそのまま実装している。

「演習」は `attempts[]` の 1 要素（`AttemptRecord`）。「課題」は `missionId`。「参加者が課題を始めた」とは、その `missionId` の演習が 1 件以上あること。

| 指標 | 分母 | 分子 | 使う項目 |
| - | - | - | - |
| 初回開始率 | 参加者数（渡された JSON の数） | 課題の演習が 1 件以上ある参加者 | `attempts[].missionId` |
| ステージ到達率（課題・ステージごと） | その課題の演習数 | そのステージに到達した演習数 | 下の「ステージの判定」 |
| ミッション完了率（課題ごと） | その課題を始めた参加者 | 再現・防御・理解の達成印がすべて `achieved` の演習を 1 件以上持つ参加者 | `badges.*.achieved` |
| 再挑戦率（課題ごと） | その課題を始めた参加者 | 同じ `missionId` で、`variantId` と `seed` の組が異なる演習が 2 件以上ある参加者 | `attempts[]` の同一 `missionId` の数、`variantId`、`seed` |
| 理解確認の正答率（課題ごと） | 理解確認に回答した演習（`answers` が空でない） | 理解の達成印が `achieved` の演習 | `answers`、`badges.understanding` |

補足：

- **ステージの判定**は `platform/progress/stages.ts` の `stageStates` と同じ（演習を保存した記録では、防御の達成印は記録上の達成で数える。XP の計算 `platform/progress/xp.ts` と同じ扱い）。

  | ステージ | 到達の条件 |
  | - | - |
  | 事件を確認 | `milestones.briefedAt` が null でない |
  | 手がかりを探す | `milestones.firstRequestAt` が null でない |
  | 脆弱性を再現 | `badges.reproduction.achieved` |
  | 対策する | `milestones.firstDefenseAt` が null でない |
  | 最終検証 | `badges.defense.achieved` かつ `badges.understanding.achieved` |

  `milestones` のない旧版（schemaVersion 1）の記録は、どのマイルストーンにも到達していないものとして読む。
- **再挑戦**は「新しいデータで再挑戦する」（別 seed）だけを数える。同じ seed のやり直し（「最初から始める」で同じ演習票を作り直した場合や「続きから始める」）は数えない。spec §5.4 の「データだけが違う再挑戦を新しい脆弱性として表示しない」のとおり、再挑戦は同じ課題の中の回数として扱う。
- **理解確認の正答率**は設問ごとの正誤ではなく、演習単位で「すべて正解して理解の達成印が付いたか」を見る。進捗 JSON には回答した選択肢 ID（`answers`）だけがあり、正解かどうかはパックの `transferCheck` にしかないため、JSON 単独で出せるのはこの粒度まで。設問ごとの誤答の傾向を見たいときは、観察セッションで画面を一緒に見て記録する。
- **「別条件での」理解確認**：理解確認の設問はすべて演習と異なる状況で出題している（spec §9「別の利用者・データ・入力文脈」）ので、理解の達成印がそのまま別条件での判断の指標になる。チャレンジモード（#75）が入ったら、別 seed の演習の正答率を同じ式で分けて出す。
- 改善履歴（`history`）と検証回数（`verifications`）は指標に使わない。回数の多さは学習成果ではない（spec §9）。

### スクリプトの使い方

```sh
pnpm run metrics <進捗JSON かディレクトリ>...             # 表で出す
pnpm run metrics --json <...>                             # JSON で出す（表計算に貼る用）
pnpm run metrics --missions idor,stored-xss,sqli <...>    # 集計する課題を絞る（練習課題を除くとき）
```

- ディレクトリを渡すと、その配下の `.json` を名前順に読む（1 ファイル = 1 人）。
- 形式が違う・壊れている・1MB を超えるファイルは、理由を標準エラーに出して飛ばす。残りは集計する。
- 分母が 0 の指標は `—（分母 0）` と出す。0% と区別する。
- スクリプトは製品コード（`platform/`）を読み込まず、進捗の形式とステージの判定を書き写している。`schema.ts`・`stages.ts` を変えたら、スクリプトと `tests/unit/evaluation-metrics.test.ts`（製品側の定数と突き合わせる検査がある）も直す。

## 3. 観察セッションで聞く指標

進捗 JSON からは出せないものは、同意のある手元の観察で聞く（spec §16）。

| 指標 | 聞き方 | 記録 |
| - | - | - |
| 翌週の再訪意向 | 「来週、続きや別の課題をやってみたいと思いますか」 | はい／わからない／いいえ、と理由を一言 |
| 再挑戦意向 | 「同じ課題を別のデータでもう一度やってみたいですか」 | はい／わからない／いいえ、と理由を一言 |
| 不十分な対策を選んだ理由 | 対策パネルで不合格になった直後に「なぜその対策で防げると思いましたか」 | 本人の言葉をそのまま。対策 ID を添える |
| 目的の理解にかかった時間 | 導入を閉じてから最初の操作（調査の送信）までを観察者が計る | 秒。導入を飛ばした場合はその旨 |
| 分かりにくかった点 | 「止まった」「戻った」「読み直した」場面を観察者が記録し、終了後に本人に確かめる | 画面名と本人の説明 |

### 手順

1. **同意**：記録するもの（操作の観察、聞き取りのメモ、本人が書き出した進捗 JSON）、使い道（この教材の改善だけ）、外部に送らないこと、途中でやめられることを伝え、同意を得る。録画・録音はしない。
2. **準備**：新しいブラウザプロファイル（進捗なし）で `pnpm run serve` か配布 ZIP を開く。観察者は画面の横で、操作に口を出さない。質問には「どう思いますか」と返す。
3. **実施**：練習課題（約 10 分）のあと、3 課題のうち 1 つ以上（1 課題 10〜20 分）。合計 45 分を目安にし、60 分を超えない。
4. **聞き取り**：終了後に 3 の表の項目を聞く。不十分な対策の理由は、その場で聞けなかった分をここで補う。
5. **書き出し**：本人に「進捗を書き出す」を押してもらい、ファイル名を参加者番号（例 `p03.json`）に変えて受け取る。
6. **集計**：`pnpm run metrics <ディレクトリ>` の出力と、聞き取りの表を 4 の形式で残す。

## 4. 記録の形式（Phase 1 前後で比べる）

機能追加の前後を同じ形式で残す。Phase 1 のチェックポイント（Issue #68）の観察結果もこの形式で書き、以後の比較の基準にする。

### 4.1 セッションの記録（参加者ごと）

| 項目 | 値 |
| - | - |
| 参加者番号 | p01 |
| 実施日・版 | 2026-10-20・コミット `abcdef0`（Phase 1 後） |
| 事前の経験 | Web 開発の経験年数、セキュリティ学習の経験（自己申告） |
| 取り組んだ課題 | onboarding、idor |
