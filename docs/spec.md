ブラウザ上で動く教材アプリに、よくあるアプリケーション脆弱性を独立した課題パックとして注入する学習プラットフォーム。利用者は事故を調査・再現し、用意された対策を適用して、攻撃の阻止と正常動作を確かめる。コード編集やAIへの指示は参加条件にしない。

仕様バージョン0.3、更新日2026年10月14日。実装前の設計仕様。0.3で初期対応ブラウザをPC版Chromeのみにし、Edgeを対象外にする。旧案の「自分のコードをローカルAIで改修して持ち込む方式」を廃止し、提供アプリと選択式の対策に変更する。本仕様の作成は実装、応募、GitHubへのアップロード、外部公開を含まない。

## 1 目的とターゲット

初期対象は、Webアプリのよくある脆弱性を学びたい初心者。AIでサービスを作るバイブコーダーも含む。HTTPやSQLの知識は短い補足で学べる構成にし、開発環境の構築経験は求めない。

利用者は次の三つを得る。

- 動くアプリの観察から、脆弱性の原因と影響を説明できる経験。

- 攻撃が成立する条件、守るべきデータ、修正の効果を判断する力。

- セキュリティ対策を加えても正常な利用が成立することを確かめる習慣。

学習中の操作はブラウザだけで完結する。アカウント登録、外部API、AIモデル、クラウドDBは不要。ローカル版は配布済みファイルをlocalhostの静的サーバで配信する。静的サーバの起動は初回準備に含み、アプリ用バックエンドの構築は不要とする。

## 2 要求とMVPの設計判断

| 項目 | MVPの決定 |
| - | - |
| 学習対象 | アプリケーションの一般的な脆弱性 |
| 教材アプリ | 提供するメモ・コメント・検索アプリ1種類 |
| 初期教材 | IDOR、保存型XSS、SQLインジェクションの3パック |
| 問題の投入 | 検証済みの脆弱な実装を指定フックへ注入 |
| 利用者の修正 | UIで対策を選択し、対応する実装を切り替える |
| 独立性 | 各パックを単独導入・開始・リセットできる |
| 同時実行 | 1演習につき有効な問題は1パック |
| 配信 | 静的配信とlocalhostで同一のビルド成果物を利用 |
| 実行方式 | ブラウザ内JS、隔離iframe、SQLite WASMを第一候補にする |
| 進捗 | ブラウザ内保存、JSONの書き出し・復元 |
| 初期対応 | PC版Chromeのみ。Edgeは対象外。検証したバージョンをREADMEへ記載 |

「毎回」は、新しいミッションまたは利用者が明示して開始した再挑戦ごとを意味する。同じ演習の修正後テストでは再注入しない。有限の検証済みバリエーションを繰り返し利用できる仕様とし、無限に新しい脆弱性を生成することは保証しない。

## 3 既存サービスとの位置づけ

ブラウザ完結、ローカル保存、ゲーム化、修正案の選択だけでは強い独自性にならない。差別化の仮説は「動いている同じサービスへ独立パックで問題を投入し、調査・対策・業務継続の確認までを体験でき、教材作者も問題を追加しやすい基盤」に置く。AWS GameDayからは状況判断と実行結果から学ぶ体験を参考にする。AWS環境やクラウド障害の再現はMVPに含めない。

| 参考例 | 重なる体験 | 本企画で検証する価値 |
| - | - | - |
| OWASP Juice Shop | 脆弱性の発見、修正案の選択 | 同じ基準アプリへ課題を投入・解除する共通契約 |
| Untrusted Security Game | ブラウザ学習、防御設定、正常系と不正系の検証 | 実際のDOM・SQL・認可処理の変化を根拠にした学習 |
| GraphQL Security Academy | ブラウザ内アプリでの攻撃と修正 | コードを書かず、原因と対策の効果を判断する入門体験 |
| AWS GameDay | 状況に応じた調査と問題解決 | 個人がローカルでも繰り返せる短いアプリ脆弱性演習 |

独自性は未検証の仮説であり、競合に存在しないとは断定しない。MVPでは学習者の理解に加えて、第2・第3パックをコアUIの改変なしに追加できるかでプラットフォームの価値を検証する。

## 4 学習の流れ

1. ミッション一覧から課題を選び、守るデータと正常な利用を確認する。

2. プラットフォームが安全な基準アプリと架空データを準備する。

3. 選択したパックが指定フックへ脆弱な実装を注入する。

4. 事前検証で攻撃成立・正常動作・対象外の安全性を確認し、同じ初期状態から演習を開く。事前検証はプレイヤーの達成には数えない。

5. 事故の状況と調査目標を確認する。演習用に問題を注入したことを画面に明示する。

6. プレイヤーが利用者の切り替えやリクエスト変更で問題を再現する。

7. 対策パネルで修正方針を選び、対応する事前実装済み処理を適用する。

8. 同じ演習で攻撃ケース・正常系・回帰テストを実行する。

9. 修正前後の挙動と参考コード差分を確認し、別条件の理解問題に答える。

10. 次の機能とミッションへ進む。

例：別ユーザーの非公開メモが見える事故を再現し、「一覧のリンクを隠す」を試すと直接取得は成功したままになる。「取得時に所有者を検証する」を適用すると他人のメモは拒否され、本人のメモは引き続き読める。選択内容と実際の動作の関係を学ぶ。

## 5 毎回脆弱性を用意する仕組み

### 5.1 生成方法

課題作者があらかじめ用意して検証した変更レシピを使う。レシピは、対応テンプレートの指定された認可モジュールなどを、同じ入出力契約を持つ脆弱な実装へ置き換える。

LLMの出力に偶然脆弱性が混ざることを前提にしない。課題を開始するために外部AIを呼び出すこともない。任意のソース全体に対して文字列置換や推測で変更を適用しない。

### 5.2 開始前の保証

| チェック段階 | 必須条件と失敗時の扱い |
| - | - |
| 安全な基準状態 | 全正常系・全セキュリティテストが通る。失敗時は基盤エラーとして停止 |
| 注入前 | パック版、アプリ版、必要機能、フック契約が一致。不一致は開始不可 |
| 注入後 | 対象の攻撃が成立し、正常系と対象外の必須テストは通る |
| 事前検証後 | 操作で変わったデータを破棄し、同じseedの脆弱な初期状態を再構築 |
| 注入失敗 | 部分適用を残さず基準状態へ戻す。プレイヤーの失敗として採点しない |

演習開始の条件は「対象の攻撃で架空の保護対象に実際に到達できる」「指定正常系が通る」「対象外の必須回帰テストが通る」の三つ。成功メッセージだけを表示して成立したように見せてはならない。

脆弱性テストは安全な状態を期待するため、脆弱な開始状態ではそのテストが失敗する。攻撃再現の確認は逆に成功する。この二つをUIとログで区別する。

保証するのは対応テンプレート・登録済み課題の範囲で開始した演習。任意のアプリへの適用や、環境が壊れた状態での強制開始は保証しない。

### 5.3 再挑戦と再テスト

演習開始時にmissionId、missionVersion、variantId、seed、appVersion、recipeVersionを固定し、attemptIdを発行する。対策構成と初期データのハッシュを保持し、各検証結果をrunIdに結び付ける。

- 修正後の再テストは同じattemptIdと初期データを使い、変更レシピを再適用しない。

- 各テストはデータを初期化して実行し、前の操作の副作用で結果が変わらないようにする。

- 「初期状態へ戻す」は当該演習の修正を破棄する操作として確認を表示する。

- 「別バリエーションで再挑戦」は新しいattemptIdを発行する。

- 別課題を始める場合は基準状態から新しい演習を作り、前の注入・対策・データを引き継がない。

- 対策構成や教材バージョンが変わったら、過去の合格を現在の状態の合格として表示しない。

### 5.4 バリエーション

MVPでは各ミッションに検証済みの開始レシピを最低1つ用意する。利用者ID、対象メモ、コメント、検索データはseedで変えられるようにする。データ変更と脆弱性の種類の変更を区別し、IDだけが変わった課題を「新しい脆弱性」と表示しない。

## 6 基盤と演習環境の分離

| 構成要素 | 責務 |
| - | - |
| 学習UI | 課題一覧、アプリ操作、対策パネル、ヒント、履歴 |
| Orchestrator | パックの検証、準備、注入、再試験、リセットの進行 |
| MissionPack | 問題、初期データ、注入レシピ、対策候補、テスト、解説 |
| RuntimeAdapter | 教材アプリの起動、操作、実装切り替え、観測、破棄 |
| Evaluator | 実行結果から再現・防御・正常系の成否を判定 |
| ProgressStore | 進捗の保存、復元、削除、JSON入出力 |

安全な基準状態S、注入後の脆弱な状態V、対策適用後の状態Fを区別する。基準アプリは不変とし、演習ごとにデータと実装構成を生成する。修正前後比較はVとFの実際の処理の差を示し、参考コードは閲覧専用とする。

各パックは必要なフックと機能を宣言する。認可取得処理、コメント描画処理、検索クエリ生成処理を初期の交換点とする。任意の既存アプリへ自動適用できる仕様ではない。新しい交換点が必要ならアプリまたはアダプターの拡張が必要になる。

画面には「学習用に脆弱性を注入した架空サービス」と表示する。ユーザーの実サービスを診断した結果として扱わない。教材データやコメントはプラットフォーム自身のDOMへHTMLとして挿入しない。

## 7 MVPの対象と対象外

| 対象 | 内容 |
| - | - |
| サービス | 非公開メモ、共有教材ページのコメント、自分のメモ検索 |
| 教材 | IDOR、保存型XSS、SQLインジェクション |
| 操作 | 利用者切り替え、入力・リクエスト変更、再現、対策選択、再テスト、リセット |
| ゲーム | 再現・防御・理解の達成印、サービスの改善履歴 |
| 学習補助 | 段階的ヒント、参考コード差分、原因と対策の解説 |
| データ | すべて架空。DBはブラウザ内の一時データ |
| 進捗 | ローカル保存とJSON入出力 |
| 機能の成長 | あらかじめ用意した機能の安全化を進捗として表示 |

MVP対象外は、ユーザーによるコーディング、任意リポジトリの持ち込み、AI連携、自動コード生成、Docker・Linux全体の演習、クラウド障害、複数脆弱性の同時注入、任意課題のアップロード、チーム対戦、ランキング、資格認定、実サービスへの診断・攻撃である。

MVPのアプリは学習用テンプレートである。本番用認証や運用要件を別途整備せず、演習の合格だけで本番公開可能と表示しない。

## 8 初期ミッション

### 8.1 ミッション1 非公開メモを守る

教材用の利用者切り替えとメモCRUDを用意する。注入対象はID指定でメモを取得する処理。ストーリーは「別の利用者の非公開メモが見えるという問い合わせ」。

- 保護対象は所有者だけが読める非公開メモ。

- 初期の脆弱性は、認証の有無だけを確認し、所有者を照合せずID指定でメモを返すこと。

- 攻撃は架空ユーザーBでユーザーAのメモを要求し、Aのメモ本文を取得する操作。

- 対策は「取得処理でセッション主体と所有者を照合」「画面のリンクだけを隠す」「すべての取得を拒否」の3候補。各候補に実際の処理を用意する。

- 正常系は所有者の取得・作成・更新・削除。

- 不正系は別ユーザーからの取得、未ログイン、存在しないID、クライアント指定のownerIdの偽装。

- 更新・削除の既存認可も回帰テストで確認する。

- 特定のユーザー名やメモIDをハードコードした修正を防ぐため、複数fixtureで検証する。

教材用の利用者切り替えは信頼された演習ハーネスがセッションを発行する方式とし、一般リクエストのuserIdやroleをそのまま認証済み情報として扱わない。MVPは実用的なログイン製品を教える範囲までは扱わない。

### 8.2 ミッション2 コメントからのスクリプト実行を防ぐ

共有教材ページのコメントを扱う保存型XSS。投稿内容を保存し、別の架空ユーザーが閲覧したときに、危険な描画処理によってスクリプトが実行される。

- 保護対象は閲覧者のページ内容と、その利用者の権限で行える操作。MVPでは実情報の窃取を行わず、隔離フレーム内の無害な実行マーカーで確認する。

- 注入はコメント描画をテキスト出力から危険なHTML解釈へ切り替える。実際のブラウザDOMで再現し、特定文字列を見つけたら成功を表示する方式にはしない。

- プレイヤーは検証済みの攻撃コメントを選んで投稿し、利用者を切り替えて閲覧する。MVPでは任意JavaScriptの入力を提供しない。イベント属性等を使う具体的な無害ペイロードは隔離PoCで確定する。

- 対策は「コメントをtextContentで表示」「scriptタグだけを削除」「コメントをすべて非表示」の3候補。本文はプレーンテキスト仕様とし、HTMLの装飾を必要としない。

- 正常系は日本語、記号、角括弧を含むコメントの保存・表示。再現用マーカーが発生せず、コメント本文が文字として残ることを確認する。

- 再検証では保存済みの攻撃コメントも表示し直す。投稿時だけの対処で過去のデータが危険なまま残らないかを学ぶ。

### 8.3 ミッション3 検索条件からの情報漏えいを防ぐ

自分のメモを探す検索機能を題材にSQLインジェクションを学ぶ。注入は検索語をSQLへ文字列結合する実装への切り替え。SQLite WASMで実際にクエリを実行する。

| 項目 | 仕様 |
| - | - |
| 再現 | 検証済みの検索入力で所有者条件を迂回し、別ユーザーの架空メモが結果に含まれる |
| 正解対策 | 検索語を値としてバインドするパラメーター化クエリ。所有者条件も維持 |
| 不十分な対策 | 特定語だけの禁止、検索機能の全面停止 |
| 正常系 | 自分のメモ検索、該当なし、日本語、引用符を含む検索 |
| 不正系 | 登録済みの複数の入力で他人の行が返らない |
| 評価証拠 | 実行したクエリ形・バインド値・返却行の所有者。選んだ対策IDだけで合否を決めない |

SQLiteの範囲の教材であり、別DB製品の構文や権限モデルまで再現したとは扱わない。

3パックはどれからでも開始できる。推奨順をIDOR、XSS、SQLインジェクションとするが、他課題のクリアを技術的な依存条件にしない。再挑戦はいつでも選べる。

## 9 ゲーム進行と学習判定

各ミッションには「再現」「防御」「理解」の三つの達成印を設ける。

| 達成印 | 条件 |
| - | - |
| 再現 | プレイヤーの操作で実際に対象の脆弱性が成立する |
| 防御 | 対策後に対象攻撃を防ぎ、正常系と必須回帰テストがすべて通る |
| 理解 | 別の利用者・データ・入力文脈で原因と有効な対策を判断できる |

ヒントは着眼点、調査方法、修正方針の3段階。利用による減点はしない。解法閲覧の有無は本人の記録として残す。理解確認は登録済みの条件と解説で判定し、自由記述をAIで採点しない。

主要な報酬は3つの達成印、教材サービスの安全化状況、改善履歴とする。表示上の成長は演習の成果であり、課題の実行順を固定しない。推奨の順路を見せてもよいが、課題をロックしない。

MVPではXP、ストリーク、時間競争を導入しない。MVP後の拡張では、XPは取り組みへの報酬、習熟度は理解度の指標として分けて扱う。XPは演習内の段階（ステージ）への到達や達成印の獲得に対して与え、同じ演習の同じ段階に二重に与えない。同じ手順の繰り返しだけでXPや習熟度が上がり続けないようにする。連続ログインの強要、時間競争、ランキングは拡張後も導入しない。週間目標を置く場合は利用者が任意に選ぶものに限り、未達で減点・喪失・警告をしない。

ステージは演出と進捗表示のための区切りであり、達成印の判定を変えない。ステージ到達が達成印を付けることはなく、クリック回数などの操作量を学習成果と混同しない。実績・称号は保存済みの記録から機械的に判定できる条件に限る。

安全化状況は、その課題の検証で実際に実行したテストの結果だけから計算し、計算方法を画面で明示する。セキュリティ全般の保証や本番運用の可能性を意味する表示にしない。

ローカル採点は利用者が改変できるため、自己学習の記録として扱う。改ざん耐性のある成績・資格・ランキングは提供しない。

## 10 画面仕様

| 画面 | 主な情報と操作 |
| - | - |
| ミッション一覧 | 学習目標、目安時間、達成印、開始、進捗入出力 |
| 開始前チェック | アプリ・パックの互換性、注入と事前検証の結果 |
| 演習画面 | 動くアプリ、架空ユーザー切り替え、操作パネル、目標 |
| 調査パネル | リクエスト相当の入力、結果、主体、対象、観測ログ |
| 対策パネル | 修正方針、適用、取り消し、参考コード差分 |
| 検証結果 | 攻撃阻止・正常系・回帰の個別結果、期待値と実測 |
| 振り返り | 原因、対策の理由、理解確認、達成印、再挑戦 |

キーボード操作、フォーカス表示、色だけに依存しない合否表示を必須とする。目安時間は1課題10〜20分。これは体験設計上の目標値。

画面の確認はPC版Chromeで行う（§2）。

実行中、テスト失敗、開始不可、ランタイムエラーを別の状態として表示する。教材のAPI表示はブラウザ内のリクエスト相当の呼び出しであり、本物のネットワーク通信を観測しているかのように表示しない。

因果表示は、ハーネスで実際に観測したリクエストとレスポンスを根拠とする。計測していない内部処理を推測して成功・失敗の原因と断定しない。詳細な認可トレースには対応モジュールの計測イベントを使い、欠落した場合はその旨を表示する。

演出（アニメーション、効果音、結果の強調表示）は、実際に観測した評価結果に連動させる。失敗したのに成功の演出を出さない。演出は利用者が無効化でき、無効化しても学習を完了できる。合否や達成は色・音だけで伝えず文字でも示し、OSの動きを減らす設定（prefers-reduced-motion）を尊重する。効果音の初期値はオフとし、音源は配布物に同梱して外部通信しない。

## 11 プラットフォームと課題の契約

プラットフォームは一覧、実行制御、注入、採点、保存を担当する。課題パッケージは説明、必要機能、初期データ、注入レシピ、対策候補、操作定義、再現条件、テスト、ヒント、解説を持つ。標準の入力・選択・リクエスト編集コンポーネントで演習UIを構成する。

実行環境はRuntimeAdapterで分離する。MVPでは一実装のみとし、Linux用や別言語用のアダプターは将来追加する。

### 11.1 MissionManifest

| フィールド | 意味 |
| - | - |
| id / version / schemaVersion | 課題ID、不変のパック版、定義形式の版 |
| title / learningObjectives | 表示名と到達目標 |
| vulnerability | 扱う脆弱性（通称・正式名・CWE・分類）。一覧は課題IDでなくこの項目で脆弱性名と分類を表示する。練習用（tutorial）では省略 |
| appCompatibility | アプリIDと対応バージョン |
| runtime / capabilities | 必要なアダプターと機能 |
| hooks / conflicts | 交換する処理と競合条件 |
| prerequisites | 必要機能。MVPでは他課題クリアを要求しない |
| fixtures / variants | 初期データとseedの扱い |
| mutationRecipes | 適用条件、脆弱な実装、注入後条件、復元方法 |
| actions / defenses | 操作UI定義と対策候補に対応する実装 |
| probes / tests | 攻撃成立の観測条件、正常系、セキュリティ、回帰 |
| hints / transferCheck / debrief | 段階的ヒント、理解確認、振り返り |

### 11.2 実行インターフェース

RuntimeAdapterはprepare、start、invoke、setImplementation、reset、stop、disposeを提供する。入力はアプリ版、パック版、fixture、seed、許可された実装ID。出力は応答、観測イベント、エラー、経過時間。任意ソースコード文字列を実行するAPIは提供しない。

MutationRecipeはappliesTo、apply、verify、revertを持ち、変更するフックと実装IDを宣言する。inject操作とプレイヤーの攻撃入力を区別する。適合しない変更を部分適用せず、失敗時は基準状態を再生成する。二重注入を拒否する。

Evaluatorは信頼済みパックのテストを専用の検証インスタンスで実行する。applyDefenseは動作を切り替えるだけで、合否を返さない。評価には実際の返却データ、DOM実行イベント、DB結果を用い、runIdと構成ハッシュを紐付ける。対策後も対象外のセキュリティを検証する。

### 11.3 拡張の範囲

同じRuntimeAdapterと対応契約で実行できる課題は、パッケージとカタログ登録だけで追加できること。コアUIの条件分岐にmissionIdを埋め込まない。

新しいOSや言語などの機能が必要な場合は、新アダプターの実装が必要になる。「あらゆる課題をデータ追加だけで導入可能」とはしない。MVPは開発者が同梱する信頼済みパックだけを扱い、利用者による任意パック実行は提供しない。

## 12 ローカル配布と開発者向け構成

公開版を提供する場合は静的HTTPS配信で起動する。ローカル版は事前ビルド済みZIPを展開し、同梱READMEに従ってlocalhost限定の静的サーバを起動する。準備後の演習はブラウザだけで行う。HTMLのダブルクリックによるfile://起動は受入対象にしない。

ローカル配布物にはHTML、JavaScript、CSS、WASM、教材、必要な画像をすべて含める。CDN、外部フォント、解析サービス、実行時の依存ダウンロードを使わない。ネットワークを切断してもlocalhost経由で新規起動から全課題を完了できることを検証する。

PWAのインストールや公開サイトのオフラインキャッシュはMVPの必須条件にしない。ローカル実行に必要な静的サーバ用ツールはREADMEで明示する。例としてPython導入済み環境では、配布物のディレクトリで `python3 -m http.server 8000 --bind 127.0.0.1` を起動する方式を検証する。

| ディレクトリ案 | 内容 |
| - | - |
| platform/ | 共通UI、実行制御、評価、保存 |
| runtimes/browser/ | ブラウザ用RuntimeAdapter |
| apps/memo/ | 教材アプリと交換フック |
| missions/idor/ | IDORパック |
| missions/stored-xss/ | 保存型XSSパック |
| missions/sqli/ | SQLインジェクションパック |
| catalog/ | 同梱パックの登録 |
| tests/ | 契約、隔離、ブラウザ操作の受入検証 |

これは将来の実装構成案であり、本仕様作成時点ではソースコードは生成しない。

実装時の成果物はソースコード、依存バージョン固定情報、ローカル配布物、README、課題作者向け契約資料、検証記録とする。READMEには準備・起動・ビルド・テスト・課題追加・制約・データ削除・依存ライセンスを記す。GitHubで共有できる構成にするが、公開操作は別途本人が決める。

## 13 状態管理と保存

演習状態はSelected、Preflight、Prepared、Explored、Repairing、Verifying、Passed、Blockedで管理する。Preparedには注入後の事前検証合格が必要。Verifying失敗はRepairingへ戻す。再現・防御・理解は別々に保持し、すべて満たしたときPassedにする。基盤エラーは学習上の不合格に数えない。

Attemptには課題・アプリ・レシピの版、seed、構成ハッシュ、再現結果、適用対策、テスト結果、ヒント利用、達成印を保存する。実行ごとにrunIdを発行する。通信イベントにもattemptIdとrunIdを付け、古い実行の応答を破棄する。

演習をまたぐ記録（ステージ到達、XP、実績の解除）は進捗ファイルの別の領域に保存し、形式の版を上げるときは旧版の読み込みを維持する。これらはAttemptの記録から再計算して照合でき、合わない場合は再計算した値を使う。演出の設定は端末ごとの好みとしてブラウザに保存し、進捗ファイルに含めない。

進捗はIndexedDB等のブラウザ保存領域へ保存し、削除・JSON書き出しを提供する。再読み込み時は保存したseedと対策構成から環境を再生成する。操作途中のDB全体の永続化は必須にせず、復帰時にデータを初期化することを表示する。

進捗JSONはサイズ・スキーマ・対応版を検証する。現在の合格を表示する前に構成を照合し、復帰後の動作は再検証する。JSONから任意コードや課題パックを実行しない。保存不可時はメモリで継続し、保存不可と書き出し方法を表示する。

## 14 実行環境と隔離

第一候補はTypeScriptの静的Webアプリ、Web Worker内の教材ロジックとSQLite WASM、XSS演習用の隔離iframe。SQLiteはメモリDBを用い、DB永続化は不要。認可処理はブラウザ内でサーバの判断をモデル化し、SQLとDOMは実エンジンで実行する。WebContainersやLinux環境はMVPの依存にしない。

ブラウザ内実行だけで外部通信遮断やホスト画面の保護が保証されるとは扱わない。次を実装の受入条件とする。

- 演習コードからプラットフォームの保存データ、DOM、認証情報へアクセスできない。

- プレビュー、実行環境、評価器の権限境界を分け、メッセージの送信元と内容を検証する。

- XSSは検証済みの固定ペイロードだけを許可し、外部送信・遷移を伴わない教材にする。iframeのsandboxとCSPで追加制限し、通信禁止を実測する。任意の攻撃コードを安全に実行できるとは保証しない。

- XSS用iframeはallow-scriptsを必要範囲で許可し、allow-same-origin、ポップアップ、トップ遷移、フォーム送信、ダウンロードを許可しない。CSPのscript制約は教材の再現性と両立する範囲をPoCで決める。

- 任意のインストールスクリプトや外部パッケージの実行を避ける。

- 各テストにタイムアウトを設け、停止・破棄・再起動できる。

- iframeからのメッセージは送信元ウィンドウ・スキーマ・実行IDを照合する。opaque originの文字列だけを信頼しない。Host上ではログと教材入力を文字列として描画する。

初期の設計上限案は進捗JSON 1MB、入力1件4KB、操作履歴1000件、テスト1件5秒、スイート60秒。超過時は理由を表示し、停止と再試行を提供する。実測値ではなく、対応端末のPoCで調整する。

ブラウザ内のモデルでは、本物のHTTPサーバ、Cookie認証、ネットワーク境界、OS権限までは再現しない。認可は実サービスではサーバ側で強制する必要があると解説する。ブラウザ内にすべて存在する教材データを、利用者自身から秘匿できるとは扱わない。

実装前PoCで、localhostの冷起動、SQLite WASMの読み込み、XSSの実行と隔離、固定ペイロードの外部通信ゼロ、停止・再初期化を確認する。XSSの再現と隔離が両立しなければ実装方式を見直す。文字列判定の疑似成功へ置き換えて実演と称さない。

## 15 受入条件

ブラウザ上の受入確認はPC版Chromeで行う（§2）。

| ID | 検証内容 | 合格条件 |
| - | - | - |
| A01 | 基準アプリ | 全正常系・全セキュリティテストが通る |
| A02 | 3パックの個別開始 | 各攻撃が成立し、正常系・対象外テストは通る |
| A03 | 非互換・注入失敗 | 開始を止め、部分変更を残さない |
| A04 | 正解対策と再テスト | 再注入せず攻撃阻止・正常系・回帰が通る |
| A05 | 全拒否・機能停止 | 正常系失敗により合格しない |
| A06 | IDORでUIだけを修正 | 直接取得が成功し不合格になる |
| A07 | IDORの認可 | 他人・未認証を拒否し、本人のCRUDを維持する |
| A08 | XSS再現 | 保存後の別ユーザー閲覧で実DOMの実行マーカーを観測する |
| A09 | XSS修正 | 保存済み攻撃が動作せず、通常コメントは表示される |
| A10 | SQLi再現と修正 | 実SQLiteで他人の行が漏れ、値バインド後は漏れない |
| A11 | SQLの正常系 | 引用符、日本語、該当なしを正しく扱う |
| A12 | 独立追加 | 第2・第3パックを共通契約とカタログ登録で導入し、コアUIに課題ID分岐がない |
| A13 | リセットと課題切替 | 基準から再構築し、他課題の状態が混入しない |
| A14 | 事前検証と本人操作 | 自動probeだけで再現バッジが付かない |
| A15 | 保存・復元 | 進捗復元、再検証、保存不可時の書き出しができる |
| A16 | 不正な進捗JSON | サイズ・スキーマ違反を拒否し、既存進捗を失わない |
| A17 | 隔離 | 固定ペイロードがHost DOM・保存領域にアクセスできず、外部送信しない |
| A18 | 実行異常 | タイムアウト・破棄・再試行ができ、偽の合格を返さない |
| A19 | ローカル動作 | 外部ネットワーク遮断・冷キャッシュのlocalhost起動から3課題を完了 |
| A20 | 証拠の整合 | 結果がrunIdと構成に一致し、古い応答を混ぜない |
| A21 | 再現性 | 同じパック版とseedで初期状態・テスト結果を再現できる |
| A22 | 操作性 | コード入力なしで完了でき、キーボードで主要操作ができる |

各課題パッケージの出荷前に、安全な基準実装は全テスト合格、脆弱なレシピは対象セキュリティテストのみ想定どおり失敗、正解修正で全テスト合格を確認する。想定外の回帰があるレシピは登録しない。

## 16 MVPの進め方と評価

実装順序は、隔離とSQLiteのPoC、IDORの縦通し、パック契約の分離、XSS、SQLインジェクション、保存・ヒント・振り返り、ローカル配布検証とする。技術PoCが成立してからMVPの開発見積もりを確定する。

学習評価では初回起動、完了率、ヒント利用、不十分な対策を選んだ理由、別条件での理解、再挑戦意向を確認する。基盤評価では追加パックに必要だったコア変更を記録する。利用履歴の外部送信はせず、初期ユーザーテストは同意のある観察・手元の記録で行う。

MVP完成はA01〜A22を満たし、3パックを単独で最後まで体験できること。学習価値は正解の選択だけでなく、原因・守る対象・正常動作を壊さない対策を別条件でも判断できることで評価する。本仕様時点では動作検証は未実施。

名称、公開先、商用化、具体的なライセンス、将来の言語・Linux対応は未決定とする。初期実装を始める際は本仕様の技術PoCから着手し、仕様作成だけで実装や公開を実施したものとは扱わない。
