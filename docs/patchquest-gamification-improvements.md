# PatchQuest ゲーミフィケーション改善提案

## 1. 目的と現状

PatchQuestは、ブラウザ上で架空アプリの脆弱性を再現し、対策を選択して動作検証する初心者向けの学習プラットフォーム。初期ミッションはIDOR、保存型XSS、SQLインジェクションの3つ。学習の判定は「再現」「防御」「理解」の3段階で、進捗はブラウザ内に保存する。

**改善目標**：教材としての正確さを維持しつつ、「触って楽しい」「成功が気持ちいい」「次へ進みたい」を実現する。単なるポイント・バッジの追加ではなく、脆弱性の発見と修正自体を面白くする。

## 4. 具体的な改善仕様

### 4.1 ストーリー型ミッション【S】

**現状**：「非公開メモを守る」など技術課題として提示。

**改善案**：架空企業のセキュリティ担当としてインシデントを解決する構成。

例：ミッション1「消えた機密情報」

> 🚨 SECURITY ALERT  
> 非公開メモが権限のないユーザーから閲覧された可能性があります。  
> 原因を調査し、情報漏えいを防いでください。  
> **MISSION START**

**設計原則**：導入は短く（30秒以内を目安）、すぐ操作できるようにする。長い会話や強制演出はスキップ可能にする。

### 4.2 攻撃・防御の成功演出【S】

- **攻撃再現時**：赤系の警告、対象データの強調、「VULNERABILITY EXPLOITED!」などの明快な結果表示。
- **防御成功時**：攻撃阻止・正常系・回帰テストが順に成功する表示、「SYSTEM SECURED!」と獲得報酬。
- **不十分な対策時**：「リンクを隠しただけでは直接取得できる」「全面停止で正常利用も失敗した」など、何が起きたかを即座に可視化。

演出は**実際に観測した評価結果**に連動させる。失敗したのに成功演出が出ることは避ける。音量・動きは設定で調整可能にし、色だけに頼らない。

### 4.3 ミッションを小ステージに分割【S】

| ステージ | プレイヤーの行動 | XP例 |
| --- | --- | ---: |
| 1. 事件を確認 | 守るべき情報・正常動作を把握する | 10 |
| 2. 手がかりを探す | 対象操作と条件を見つける | 20 |
| 3. 脆弱性を再現 | 実際の結果で攻撃成立を確認する | 30 |
| 4. 対策する | 修正方針を選び適用する | 30 |
| 5. 最終検証 | 攻撃阻止・正常系・回帰・理解確認を通す | 50 |

XP値は仮置き。**達成印「再現」「防御」「理解」の判定は既存の厳密な評価を維持**し、クリック回数などを学習成果と混同しない。

### 4.4 ワールドマップ【A】

```text
      🏆 SECURITY MASTER
               │
       🔒 SQL Injection
               │
         🎁 BONUS
               │
           ⚡ XSS
               │
           🛡️ IDOR
               │
          🚀 START
```

おすすめの順路を示しつつ、既存仕様どおり3ミッションを好きな順序で開始できるようにする。

### 4.5 XP・レベル・習熟度【A】

XPは**取り組みへの報酬**、習熟度は**理解度の指標**として分ける。

| スキル | 表示例 | 判定根拠 |
| --- | --- | --- |
| アクセス制御 | Lv.3 / ★★★☆☆ | IDORの再現・防御・別条件の理解 |
| XSS対策 | Lv.2 / ★★☆☆☆ | 安全な描画と正常表示の検証 |
| SQLインジェクション | Lv.1 / ★☆☆☆☆ | クエリの修正と結果確認 |

単に何度も同じ手順を繰り返しただけで習熟度が上がり続けないようにする。

### 4.6 サービス安全化の可視化【A】

修正前後で架空サービスの状態を表示する。

```text
SECURITY STATUS
Before: 🔴 🔴 🔴 🔴 🔴  20%
After : 🟢 🟢 🟢 🟢 🔴  80%
```

数値は演出用の例。実装時はチェック対象と計算方法を明示し、セキュリティ全般の保証や本番運用可能性を意味しないことを伝える。登場人物からの感謝、修復履歴、機能解放なども候補。

### 4.7 実績と復習【A〜B】

- 「初めて脆弱性を再現」「ヒントなしで防御」「正常機能を壊さず修正」などの実績。
- 前回学んだ脆弱性について1問だけ解く復習モード。
- 毎日のログインを強要せず、週2〜3回など選べる週間目標。
- チャレンジモードは問題の見た目だけを変えるのではなく、**別条件でも正しく判断できるか**を検証する。

## 5. 推奨実装ロードマップ

| フェーズ | 取り組み | 開発負荷（概算） | 期待効果（仮説） |
| --- | --- | --- | --- |
| **Phase 1** | ミッション導入の物語化、操作結果の演出、段階進捗 | 小〜中 | 大 |
| **Phase 2** | マップ、XP・レベル、称号、安全化の可視化 | 中 | 中〜大 |
| **Phase 3** | 復習クエスト、習熟度の精緻化、別条件チャレンジ | 中〜大 | 中 |

### Phase 1の最小受入条件

1. 初見ユーザーがミッションの目的を短時間で理解し、すぐ操作を始められる。
2. 攻撃成功・失敗・防御成功の違いが、画面表示と実際の評価結果で一致する。
3. ミッション内で少なくとも数回、意味のある達成フィードバックを得られる。
4. 演出を無効化しても学習を完了できる。
5. 既存の「再現・防御・理解」の評価、外部通信なし、ブラウザ内進捗保存を維持する。

## 6. 効果の検証

機能追加後は、初回開始率、各ステージ到達率、ミッション完了率、翌週の再訪意向、再挑戦率、別条件での理解確認の正答率を比較する。ランキングや連続ログイン数のみを成功指標にしない。

## 7. 結論

PatchQuestに必要なのは、**①操作する楽しさ（Brilliant型）→ ②成功する楽しさ（Kahoot!型）→ ③成長する楽しさ（Duolingo型）**の順で強化すること。最初にストーリー・即時演出・小ステージ化を実装し、脆弱性の発見と修正そのものが楽しい体験を目指す。
